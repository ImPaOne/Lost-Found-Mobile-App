1. SCREEN: Home Dashboard
--------------------------------------------------------------------------------
* Screen Name: Home Dashboard
* Frontend UI Files:
  - Main Layout: app/src/main/res/layout/fragment_home.xml
  - Item Layouts: app/src/main/res/layout/item_urgent_slider.xml, app/src/main/res/layout/item_report_card.xml
  - Kotlin UI Class: app/src/main/java/com/group3/lostandfound/HomeFragment.kt

* Backend Architecture Files:
  - ViewModel: app/src/main/java/com/group3/lostandfound/viewmodel/HomeViewModel.kt
  - Repository: app/src/main/java/com/group3/lostandfound/repository/ItemRepository.kt
  - Database Manager: app/src/main/java/com/group3/lostandfound/FirebaseManager.kt
  - Data Models: ReportItem, AnalyticsSummary in app/src/main/java/com/group3/lostandfound/Models.kt

* UI Components & Features:
  - Top header showing user greeting ("Hello, [Name]") and notification bell icon with unread count.
  - Search bar that takes the user directly to the Explore screen when tapped.
  - Horizontal carousel slider showing urgent lost items that have high cash rewards.
  - Quick action buttons: "Report Lost Item" (Red button) and "Report Found Item" (Navy button).
  - 6-icon category grid (Electronics, Wallets, Documents, Keys, Bags, Pets) to filter items quickly.
  - Live community feed displaying the most recent lost and found reports.
  - Fixed 5-tab bottom navigation bar for quick access across the app.

* Backend Logic:
  - HomeViewModel asks ItemRepository to stream the items list from the Firebase Realtime Database.
  - The query orders items by timestamp and takes the latest 30 items.
  - Filter logic hides flagged items (isFlagged == true) and already resolved items.
  - High-reward lost items are placed into the urgent carousel list.

    * Reporter name and contact info.

    * Changes /items/{itemId}/status to "APPROVED".
    * Sets isFlagged = false.
    * Writes an entry to /admin_logs recording who approved it.
  - When the admin taps "Reject":
    * Changes status to "REJECTED" or removes the item completely.
    * Deducts 10 Trust Points from the user who submitted the bad report (/users/{userId}/trustScore).
    * Writes an entry to /admin_logs.

================================================================================
BACKEND FILES & ARCHITECTURE EXPLANATION
================================================================================

1. HomeViewModel.kt
   - Role: ViewModel for the Home screen.
   - Why it is used: It manages UI state, holds the live list of reports and urgent carousel items, and keeps data alive during screen rotation so network requests are not repeated unnecessarily.

2. DetailsViewModel.kt
   - Role: ViewModel for the Item Details screen.
   - Why it is used: Handles loading item details, reporter data, and managing case resolution actions without cluttering the UI fragment code.

3. ReportsViewModel.kt
   - Role: ViewModel for My Reports screen.
   - Why it is used: Manages the active vs resolved report lists for the current user and triggers delete and status update commands.

4. ItemRepository.kt
   - Role: Data repository for lost and found items.
   - Why it is used: Separates Firebase database calls from the ViewModels. Handles querying items, sorting, and filtering.

5. ReportRepository.kt
   - Role: Data repository for managing user reports.
   - Why it is used: Handles deleting reports from Firebase, changing statuses, and updating user report counts.

6. FirebaseManager.kt
   - Role: Central Firebase helper class.
   - Why it is used: Provides references to Firebase Realtime Database nodes, handles offline synchronization, and keeps database logic consistent in one place.

7. FCMService.kt
   - Role: Firebase Cloud Messaging & Local Notification service.
   - Why it is used: Builds and displays high-importance notification banners on the device when an item case is resolved or updated.


================================================================================
FIREBASE OPERATIONS USED BY THIS STUDENT
================================================================================

1. Realtime Database Nodes Accessed:
   - /items
     * What it is: The root node where all lost and found item reports are stored.
     * Why it is accessed: To load recent reports on the home screen, filter urgent items, and calculate system analytics.
   - /items/{itemId}
     * What it is: The record for a specific item.
     * Why it is accessed: To read full details of an item on the Details screen.
   - /items/{itemId}/status
     * What it is: The current status of the item ("PENDING", "APPROVED", "REJECTED", "RESOLVED").
     * Why it is accessed: To update the status when an admin approves/rejects an item or when an owner marks it resolved.
   - /items/{itemId}/isFlagged
     * What it is: A boolean flag indicating if an item has been reported by the community.
     * Why it is accessed: Filtered on Home screen to hide bad content; updated in the Moderation Queue.
   - /users/{userId}
     * What it is: The profile data of a user.
     * Why it is accessed: To display reporter name, avatar, and join date on the Details screen.
   - /users/{userId}/trustScore
     * What it is: The trust points score of a user.
     * Why it is accessed: Awarding +20 points when an item is reunited, deducting 10 points when a user posts fake/flagged content, and manual admin adjustments.
   - /users/{userId}/isBanned
     * What it is: A boolean flag showing if a user account is suspended.
     * Why it is accessed: Toggled by the admin in User Management to ban or unban malicious users.
   - /admin_logs/{logId}
     * What it is: Audit log records of administrative actions.
     * Why it is accessed: Admin Dashboard and Moderation Queue write logs here whenever an admin approves, rejects, bans, or adjusts points.
   - /announcements
     * What it is: Broadcast announcements created by administrators.
     * Why it is accessed: Displays global notices across the app.
   - /analytics_summary
     * What it is: Summary metrics node.
     * Why it is accessed: Used by Admin Dashboard and Analytics screen to read and display platform statistics.

2. Read & Stream Operations:
   - ValueEventListener on /items with .orderByChild("timestamp").limitToLast(30)
     * Why: Streams the latest 30 items for the home feed and urgent carousel.
   - ValueEventListener on /items/{itemId}
     * Why: Fetches live data for the item details screen.
   - ValueEventListener on /users
     * Why: Streams all user accounts for the User Management screen so the admin can search and manage them.
   - ValueEventListener on /admin_logs
     * Why: Displays a real-time list of recent admin actions on the Admin Dashboard.
   - ValueEventListener on /items for Analytics
     * Why: Scans reports to calculate reunion success rates and category distributions.

3. Create & Write Operations:
   - Writing to /admin_logs/{actionId}
     * Why: Stores audit records with timestamp, admin email, action type, and target ID whenever an admin performs a moderation action.
   - Writing to /announcements
     * Why: Allows admins to publish broadcast announcements to all users.

4. Update Operations:
   - Updating /items/{itemId}/status
     * Why: Changes status to "APPROVED", "REJECTED", or "RESOLVED".
   - Updating /items/{itemId}/isFlagged
     * Why: Resets flag to false when an admin approves a reported item.
   - Updating /users/{userId}/trustScore
     * Why: Increases trust points (+20) when a case is solved; reduces points (-10) for bad behavior.
   - Updating /users/{userId}/isBanned
     * Why: Changes account status to true/false when admin bans or unbans a user.

5. Delete Operations:
   - .removeValue() on /items/{itemId}
     * Why: Allows users to permanently delete their own reports from the "My Reports" screen, and allows admins to remove rejected spam items.
